# Founding procedure

Build a reviewed tag with `make archive archive_tag=<VERSION_TAG>`. Verify the
archive SHA-256 and its contained SHA256SUMS before installing `vaultd` in
`/usr/local/bin`. `vaultd version` reports the tagged commit, tag, source archive
SHA-256 and deterministic packaging inputs. The final release archive digest is
computed outside the binary to avoid a circular hash. An ordinary `make build`
reports its commit and leaves archive inputs as unversioned.

Create the dedicated `vault-chain` service user and its `/var/lib/vault-chain`
home. Run every command as that user with an explicit `--home`. Each node runs:

```sh
vaultd init <MONIKER> --chain-id vault-1 --home <NODE_HOME>
vaultd comet show-node-id --home <NODE_HOME>
vaultd comet show-validator --home <NODE_HOME>
```

Only export the node ID and consensus public key. Keep the generated signing
material on its node. The SDK `keys` commands are available; the test keyring is
allowed for consensus-key-only nodes that hold no account signing authority.
Never use it for the founding admin. This chain has auth accounts but no bank,
coins, staking gentxs or fee deductions. `0nofee` matches the reference default.
Application configuration adds no environment variables; the SDK's inherited
client/server environment handling remains. Prefer explicit flags and TOML.

Use four founding hosts, with at most one validator per failure domain.
Each founder has equal voting power. One coordinator assembles genesis using the public consensus keys and the
reviewed provider owner addresses. The public key argument is the base64 value
from `show-validator`, not its surrounding JSON:

```sh
vaultd genesis add-validator <CONSENSUS_PUBLIC_BASE64> <POWER> <PROVIDER_ID> \
  --owner <PROVIDER_OWNER> --founding --home <COORDINATOR_HOME>
vaultd genesis add-genesis-account <ACCOUNT_ADDRESS> --home <COORDINATOR_HOME>
vaultd genesis collect --home <COORDINATOR_HOME>
vaultd genesis validate --home <COORDINATOR_HOME>
sha256sum <COORDINATOR_HOME>/config/genesis.json
```

Repeat add-validator for every founder. Add-genesis-account is optional and adds
only an auth account. The admin auth account is created by InitChain if absent.
The CLI adds the matching vault provider record with each validator. Keep the
initial admin at `chainprefix.GenesisAdmin`: its hub address bytes become the
vault-prefixed account on chain. No pending rotation is permitted at founding.
Both storage gates must be false. `collect` writes compact canonical JSON;
`validate` checks the module invariants, admin, storage gates, provider matching,
and exactly four founding validators of equal power, with no non-founding
validator. Preserve those exact bytes when distributing the
same genesis to every node and compare each SHA-256 before starting.

The founding CLI enforces this four-founder layout in addition to the inherited
founder-loss rule. Qualify the
four-node local network with four distinct commit signatures at every sampled
height after startup and a height above 20. Stop one node, then require several
new committed heights with the remaining three signatures. The existing offline
single-node scenario does not establish this membership liveness.

The TOML files in this directory are overlays for the files generated by init.
Replace all placeholders and merge each section into the generated file; do not
append duplicate sections. RPC, API and gRPC remain on loopback. The profiling
listener is disabled (`pprof_laddr = ""`); retain that setting when merging into
an existing home. Pruning keeps
100000 recent heights and runs every 10 heights. Telemetry and peer exchange are
off (`pex = false`). Each founding node pins the other founding nodes by node
ID in `persistent_peers`, using reviewed `<NODE_ID>@<P2P_ENDPOINT>` entries.
Keep `pex = false` on every founding node. P2P binding and port can be overridden at startup:

```sh
vaultd start --home <NODE_HOME> --p2p.laddr tcp://<P2P_BIND>:<P2P_PORT>
```

Render the service template before installing it. It restarts on failure and
stops with SIGTERM. On an isolated local test machine, use distinct ports from
47000–47999, bind all listeners to 127.0.0.1, disable the strict address book and
allow duplicate peer IPs for the local processes only. Start the real binary once
per home, retain child PIDs, and stop and wait for every child on all exit paths.
Do not run operational network qualification inside `go test`.

# Commands

All vault message commands accept one bounded protobuf JSON message file:
`tx vault link-account`, `set-storage-choice`, `commit-root`, `grant`, `revoke`,
`register-frontend`, `remove-frontend`, `update-params`, `activate-provider`.
Fields match `proto/vault.proto`; byte fields use base64 and integer fields use
protobuf JSON conventions. Supply `--from`, `--chain-id vault-1`, `--home`,
`--node`, and the intended keyring backend. Link-account needs the owner's hub
link proof described in CHAIN-CONTRACT.md. Fresh owners sign offline with the
specified first-contact account number and sequence zero, then broadcast; the
SDK account query cannot find an account before its first link is committed.
For unsigned offline generation, use `--generate-only --offline` with the
account number and sequence, and leave the chain ID empty (including in the
client configuration). The SDK rejects a nonempty chain ID in that combination.
The transaction chain-id flag has no default; `init` still defaults to vault-1.
Supply `--chain-id vault-1` to `tx sign` and `tx multi-sign`, which bind the
signatures to the chain. Online generation may use `--chain-id vault-1` without
`--offline`.

`query vault where <OWNER>` returns the canonical metadata record as base64.
`query vault may-read <OWNER> <GRANTEE> <SALT_BASE64> <SCOPE>` checks a private
read witness against committed grants. Keep witness arguments and terminal
history private. `query validatorset admin`, `validators`, and `validator` use
the inherited AutoCLI. `tx validatorset set-admin` and `accept-admin` expose
the two-step rotation: `set-admin <NEW_ADMIN>` proposes and `accept-admin`
accepts using the account selected by `--from`.
The old admin must be refused after acceptance. Verification of that transition
requires signatures from an authorized admin; a public genesis address alone
cannot produce them. A synthetic local admin fixture does not prove control of
the fixed founding admin.

# Scratch signing qualification

Use the release binary for the four-node network and genesis-admin query. For
admin rotation, create a separate scratch source copy and replace only its
GenesisAdmin constant with the address of a newly generated 2-of-3 multisig.
Create three throwaway secp256k1 accounts with `keys add`, then `keys add admin
--multisig member-a,member-b,member-c --multisig-threshold 2 --nosort` using only
the scratch test keyring. Build that fixture separately; never package it as the
release binary. Give the pending multisig an auth account in scratch genesis.

Generate SetAdmin, AcceptAdmin and UpdateParams unsigned transactions through
the CLI. Sign each with two constituents using `tx sign --multisig <ADDRESS>
--sign-mode amino-json`, combine with `tx multi-sign --sign-mode amino-json`,
then broadcast and check committed results and state. Refuse one signature,
a non-admin, the wrong chain ID and a replay. The scratch fixture also exercises
the coordinator's sign-document path and a single-signer amino AccountLink.
This proves wire compatibility using throwaway authority only.

## Provider recovery qualification

This recovers one lost founder; two lost at once halts the chain, and no admin message can land on a halted chain.

While a slot is vacant the remaining three have no fault margin; refill quickly.
A replacement host keeps the rule of at most one founder per failure domain.

Use the current admin's two constituent signatures to submit `vault
remove-provider`, then `vault replace-provider-owner` naming the replacement
host's owner. The named owner submits `vault activate-provider` for the same
provider ID with a new consensus public key and its possession proof. The
refilled slot retains its founder status and original voting power. Retired
consensus public keys cannot be reused. A second removal is refused until the
vacant slot is refilled.
